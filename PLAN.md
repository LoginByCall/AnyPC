# План: «только просмотр» и звук (аудиоконференция)

Источник — просьба владельца 2026-11-10. В ТЗ звук записан как «вне объёма… отдельным ТЗ» (TZ.md:30), поэтому требования ниже — черновик расширения ТЗ. Он вступает в силу после ответа на ASK в конце файла.

## Требования (черновик)

| ID | Требование | Критерий приёмки | Проверка |
|---|---|---|---|
| REQ-F-20 | Сессия «только просмотр»: видео идёт, ввод, буфер и файлы от клиента хост отбрасывает **на своей стороне** | 100 % событий input/clip/file в режиме просмотра не доходят до хоста; на плашке — «только просмотр» | e2e-тест (браузер → хост) |
| REQ-F-21 | Микрофон в обе стороны; каждый участник сам включает и выключает свой: хост — в окне AnyPC, клиент — в клиенте (программа и веб) | задержка звука ≤ 400 мс на P2P; эхо на хосте не слышно (на слух) | V1: Chrome с фейковым микрофоном, байты audio в обе стороны > 0; V3 — живые устройства |
| REQ-F-22 | Микрофон хоста включается только кнопкой в окне AnyPC на хосте; пока он включён, это видно на плашке | без согласия — 0 байт аудио с хоста; индикатор 🎤 на плашке всё время, пока идёт звук | e2e-тест + V3 |
| REQ-F-23 (позже) | Системный звук хоста → клиенту | — | после REQ-F-21 |

Обратная совместимость (A2 #9 — изменения только добавляющие): старый клиент не знает полей `view` и аудио, и сессия у него идёт как раньше. Старый хост не предлагает аудио, у клиента кнопка «Включить звук» скрыта.

## Маршрут звука (trade study)

| | A. Звук в Go на хосте | B. Звук на странице хоста (рекомендую) |
|---|---|---|
| Как | miniaudio (malgo) + libopus + шумодав/эхоподавление speexdsp, cgo на 3 ОС | Окно хоста — уже веб-страница (WebView2 на Windows, браузер на Linux/Mac): getUserMedia + второй RTCPeerConnection только для звука, сигнализация через канал `ctl` |
| Эхоподавление | speexdsp — слабое, настраивать вручную | встроенное в браузер (AEC3 из WebRTC), плюс шумодав и АРУ |
| Объём | ~1500 строк, 3 новые C-зависимости, кросс-сборка | ~300 строк JS + ~50 Go, новых зависимостей нет |
| Риски | качество эха, сборка под Mac/Windows | окно хоста должно быть открыто (на Linux/Mac это вкладка браузера); разрешение на микрофон в WebView2 [ПРЕДПОЛОЖЕНИЕ: запрос по умолчанию — проверить spike'ом] |
| Обратимость | тяжело откатить | легко: всё отдельно от видео |

Системный звук (REQ-F-23) на маршруте B — через getDisplayMedia({audio}). Это только Windows/Chrome и каждый раз с запросом [ПРЕДПОЛОЖЕНИЕ]. Решаем после конференции.

## Этапы (по убыванию риска)

1. **Spike звука, лимит одна сессия.** На странице хоста в WebView2: микрофон, второй PC через `ctl`, звук доходит до браузера клиента. Результат — знание (код выбрасывается). Если не получится → маршрут A, ASK заново.
2. **«Только просмотр» (REQ-F-20).** Флаг сессии на хосте: канал `input` и `clip` от клиента игнорируются, файловые каналы от клиента не принимаются, текст плашки меняется. У клиента галочка «Только просмотр» перед подключением (`connect.view`). Окно «Разрешить» получает 3 кнопки (Да/Нет/Отмена → «Разрешить / Только просмотр / Отклонить»; zenity `--extra-button`, osascript — 3 кнопки). Тест: TestBrowserClient в режиме просмотра — ввод и буфер не дошли.
3. **Конференция (REQ-F-21/22) по итогам spike.** Кнопка «Включить звук» у клиента, согласие на хосте, 🎤 на плашке, выключение с любой стороны.
4. Выпуск — ASK (гейт).

### Протокол звука (этапы 1 и 3, только добавления)

- Хост объявляет поддержку в сообщении `ok` после входа: `"audio": true`. Нет поля → у клиента кнопки микрофона нет (старый хост).
- Клиент после входа сам открывает второй RTCPeerConnection (`audio` sendrecv, без трека — микрофон выключен) и шлёт по `ctl`
  `{"t":"audio","sdp":<offer>}` целиком, без trickle (ждём конца сбора кандидатов: окно хоста опрашивает раз в секунду).
- Go-хост не разбирает SDP: кладёт предложение в `hostInfo().audio = {cid, sdp}`; окно хоста отвечает `audioAnswer(sdp)`,
  хост пересылает `{"t":"audio","sdp":<answer>}`. Окно хоста закрыто → через 5 с `{"t":"audio","err":"closed"}`.
- Микрофон у каждого свой и **по умолчанию выключен** (владелец 2026-11-10): кнопка 🎤 → getUserMedia → `sender.replaceTrack`.
  Выключение — `replaceTrack(null)` и остановка трека (индикатор записи ОС гаснет).
- REQ-F-22: пока микрофон хоста включён, хост знает это из `audioMic(true/false)` окна и показывает 🎤 на плашке.
- Только просмотр не отключает звук (звук — не управление).
- Тест V1: два headless Chrome с `--use-fake-device-for-media-stream`, хост — страница окна на локальном сервере: байты audio
  в обе стороны > 0 после включения микрофонов, 0 — пока выключены. V3 (владелец): WebView2 спрашивает разрешение на микрофон.

## Риски

- Окно хоста закрыто или свёрнуто в трей → звука нет. Митигация: «Включить звук» отвечает клиенту «на хосте не открыто окно AnyPC».
- Оператор управляет мышью хоста и может сам нажать «разрешить микрофон» → согласие спрашивается до начала управления или в окне «Разрешить»; 🎤 на плашке не отключается.
- Эхо при громкой связи через динамики → маршрут B (браузерное эхоподавление); проверка V3.

# План: учётные записи с правами на хосте (владелец 2026-11-10: «вариант входа — учётные записи с правами»)

| ID | Требование | Критерий приёмки |
|---|---|---|
| REQ-S-20 | На хосте несколько учётных записей: имя, свой пароль (Argon2id), права: `полный` / `просмотр` (дальше — файлы, буфер отдельно) | вход каждой записью своим паролем; права «просмотр» = REQ-F-20, хост соблюдает их сам |
| REQ-S-21 | По ответу хоста нельзя узнать, есть ли такое имя | для неизвестного имени — поддельная соль HMAC(ключ хоста, имя); время ответа то же |
| REQ-S-22 | Блокировка перебора по имени и по хосту | как REQ-S-04, раздельные счётчики |
| REQ-F-24 | Имя пользователя — на плашке и в журнале сессий | видно всё время сессии |

Совместимость: старый клиент без имени входит как пользователь по умолчанию с нынешним паролем; старые настройки (одно поле Hash/Salt) переводятся в запись по умолчанию. Изменение протокола — поле `user` в первом сообщении auth (только добавление).
Объём: 1–2 сессии (config, CPace по записи, окно хоста «Пользователи», ключи `--user имя --password-stdin`, клиент — поле «Имя», тесты перебора и подделки соли).
Перед началом — ASK (A2 #10, вход и криптография): формат поддельной соли и порядок сообщений auth; дефолт — соль HMAC-SHA256(ключ хоста, имя)[:16], `user` в сообщении "a".
