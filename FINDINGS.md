# Ключевые находки проекта AnyPC

Что выяснено замером, отладкой или ревью и не очевидно из кода. Формат: утверждение → условия → доказательство.
`[вывод]` — выведено, не измерено; `[ПРЕДПОЛОЖЕНИЕ]` — не проверено. Новые находки дописываются сюда сразу,

## Видео: передача и адаптация

- **Кадр, отправленный пачкой, теряется на приёмнике, а не в сети.** Пачка 400 × 1,2 КБ Мак → Linux по гигабитной
  LAN: буфер приёма 208 КБ (по умолчанию) — потери 20–30 %; буфер 4 МБ — 0 %; та же пачка в темпе 10 Мбит/с
  при буфере 208 КБ — 0 %. Пинг при этом 0 % потерь. Условия: UDP, приёмник не успевает вычитать сотню пакетов.
  Доказательство: LOGBOOK 2026-11-10. Следствие: нужен темп отправки (agent/pace.go).
- **Ложные потери обрушивают поток.** Контроллер (rate.go) видит 11–20 % потерь и режет 4000 → 300 кбит/с, в режиме
  «Качество» вместе с ним падает частота до 5 к/с; на 300 кбит/с новый экран текста дорисовывается до 40 дБ
  3,8–6,7 с. Это и есть «фризы и обновление картинки 7–8 с» на Маке (отчёт владельца 2026-11-10, журнал хоста).
- **Пейсер pion (gcc.LeakyBucketPacer) не решает задачу:** копит бюджет в простое (`budget` от последней отправки)
  и выпускает следующий кадр той же пачкой; очередь без предела. Доказательство: исходник interceptor v0.1.51.
- **Пейсер должен стоять выше TWCC/GCC** в цепочке интерсепторов (регистрироваться последним), иначе задержка
  пейсинга попадёт в замер задержки сети и GCC увидит ложную перегрузку. `[вывод]` из устройства pion Chain.
- **Рост после падения был слишком медленным:** +30 % раз в 20 с хорошего канала → 300 → 4000 кбит/с больше 3 мин.
  Пауза нужна только ffmpeg (шаг = перезапуск); кодеру в процессе — 3 с (TestRateFast).
- **GCC на чистой LAN занижал оценку до 300–400 кбит/с при 0 % потерь** (H.264, v0.1.13) — пачки кадров дают
  разброс задержки прихода. `[вывод]`: лечится тем же темпом отправки.

## Видео: кодеки (замеры на тексте 1080p, LOGBOOK 2026-11-09/10; повтор — agent/vp9bench.sh)

- **x264 ABR с IDR раз в секунду портит статику:** PSNR пилой 21–34 дБ на 500 кбит/с. CRF 20 + потолок VBV без
  периодических IDR — 31 → 61 дБ монотонно, статика 16 кбит/с.
- **intra-refresh x264 хуже:** каждая волна перекодирует хорошую картинку при QP 39–44 (45 → 30 дБ каждые 3 с).
- **VP9 (libvpx, screen) лучше x264 на тексте и движении:** дорисовка вдвое быстрее, на движении +1 дБ при 72 %
  битрейта; CPU ≈ 1 ядро на 1080p30 (Linux 16 ядер 3,6 мс/кадр, Мак Xeon 2012 7,0 мс/кадр). OpenH264 упирается
  в 44 дБ; SVT-AV1 2.3.0 из ffmpeg в CBR не выдал поток.
- **libvpx в режиме CQ не держит размер кадра:** смена картинки — кадр 110–175 КБ (15–42 средних), на статике
  периодические кадры до 175 КБ. VP9E_SET_MAX_INTER_BITRATE_PCT в CQ не действует (замер). Строго держит только CBR.
- **libvpx CBR с MinQ 2 тратит 1–1,3 Мбит/с на статичном экране** (дорисовывает до ~60 дБ бесконечно);
  MinQ 10 — 80 кбит/с и потолок ≈ 50 дБ, MinQ 16 — 25 кбит/с и ≈ 47 дБ. Выбрано: CBR, MinQ 10, AQ 3,
  ключевой ≤ 300 мс потока (как libwebrtc). Наибольший кадр 28 КБ, 40 дБ за 0,4 с на 4 Мбит/с.
- **Пропуск кадров кодером (rc_dropframe_thresh) на смене текста только замедляет дорисовку** — выключен.
- **В режиме «Качество» источник VP9 застревал на 5 к/с** после смены профиля: ffmpeg запускался с частотой
  rate.fps(); исправлено — источник всегда на полной частоте, прореживает streamVP9.
- **Курсор в кадре делает статику «движущейся».** Курсор отдельно по ctl: при движении одной мыши видео статично.

## Клиент и вход

- **«Запомнить пароль» не срабатывал при повторном входе, и с именем это выглядело как «неверное имя или пароль».**
  Клиент стирает пароль из поля при входе («ok»), а запомненный подставлял только на ввод ID (`oninput`). После
  «Разорвать» ID в поле остаётся — повторное «Подключиться» уходило с пустым паролем: «fail» хоста (и лишняя неудача
  в счётчике перебора), с именем — текст «неверное имя или пароль». Исправлено: после сессии запомненный пароль
  подставляется снова, без пароля вход не начинается. Доказательство: TestBrowserUsers (refill/again/nopw), до правки —
  `again=Error: wrong name or password`. Доска владельца 2026-11-11, обе карточки ToDo.
- **Записи по имени не действуют не только при галочке «Спрашивать»,** но и когда у записи по умолчанию нет TOTP
  (`codeModeLocked`: `Users[0].TOTP == ""`) — свой TOTP записи не помогает. Ответ хоста тот же «fail» (REQ-S-21/23),
  клиент пишет «неверное имя или пароль» — с 2026-11-11 с подсказкой про эти два случая. Источник: app/config.go codeModeLocked, TZ.md REQ-S-23.

## Платформы

- **Windows: DXGI_ERROR_ACCESS_LOST (887a0026)** через секунды после старта (UAC, блокировка, полноэкранное окно) —
  захват надо перезапускать; регрессия TestCaptureRestart.
- **macOS avfoundation не слушает -framerate для экрана:** ~420 к/с с ложными метками, серый кадр у клиента; нужен
  фильтр fps. Экран Мака в точках, Retina — пикселей вдвое больше.
- **macOS: системный курсор не сравнить по объекту** (NSCursor.currentSystemCursor — копия) — форма не определяется.
- **macOS: сетевые e2e-тесты агента на en0 плавают** (ICE висит в UDP WriteTo, и на v0.1.5). `[ПРЕДПОЛОЖЕНИЕ]`:
  LuLu держит пакеты нового неподписанного бинарника до ответа на запрос. Не проверено.
- **macOS: процесс, запущенный по ssh, не получит «Запись экрана»** (разрешение выдано Терминалу) — хост на Маке
  перезапускает только владелец из Терминала. `[вывод]`
- **Wayland: курсор рисует портал** (cursor_mode 2), отдельно его не отдать.

## Сборка и выпуск

- **libvpx для Windows требует mingw g++** (vp9/ratectrl_rtc.cc — C++); у configure нет `--cross`, префикс —
  переменной CROSS; mingw-libvpx тянет winpthreads → `-lpthread` на всех платформах, кроме darwin.
- **На Маке ld берёт libvpx.dylib, если она рядом с .a** (Homebrew) — в каталоге lib только libvpx.a; build.sh
  проверяет otool -L.
- **Статический Linux-бинарник с cgo:** `-tags netgo,osusergo -extldflags -static`, иначе glibc getaddrinfo.
- **Тег, уже отправленный на GitHub, перенести нельзя** (классификатор) — новый номер выпуска.
- **Каждый выпуск: MIN_VERSION в deploy/setup.sh = версии тега** в том же коммите, иначе publish.sh откажет.
- **zsh не разбивает строку переменной на аргументы** (`./bench.sh $cfg`) и понимает `$F:t` как модификатор —
  скрипты стенда гонять через bash.
- **GStreamer x264enc tune=zerolatency режет кадр на слайсы по числу потоков** (176 слайсов на 10 кадров), а мы ставим
  длительность сэмпла на каждый слайс: браузер показывает верхнюю полосу кадра и вертикальные полосы ниже (Wayland-хост,
  2026-11-10). Нужно `sliced-threads=false`, как `-x264-params sliced-threads=0` у ffmpeg. Тест TestGstTail.
- **Захват на Wayland (portal_linux.go) не смотрел на Cap.VP9** — всегда H.264; кодер VP9 в процессе ждал Y4M → чёрный
  экран при «Турбо». Новый тип захвата — проверять обе ветки Cap (H.264 и VP9).
- **Любая правка встроенного скрипта ui/index.html (даже комментария) ломает хэш в CSP** — браузер молча не запускает
  скрипт, браузерные тесты падают с пустым результатом. Новый хэш печатает `go test ./ui` (TestCSPHash) — гонять
  `go test ./...`, а не только ./agent.
- **Текст ошибки, который присылает хост, — на языке хоста** (2026-11-10): отказ «только просмотр» при перетаскивании файла
  показывался по-русски в английском клиенте. Клиент проверяет режим сам и пишет из своего словаря; текст хоста — только

  новый CreateSession; при «Отмене» в окне GNOME окно появится снова. На GNOME 50 бывает и «Session creation inhibited»

## Готовые решения для состава группы — исследование 2026-11-14

Вопрос владельца: есть ли известные алгоритмы управления составом группы и обхода коллизий. Условие владельца: брать готовое, если open source под MIT.
- **Ключевое наблюдение `[вывод]`:** украденный ПК не может подписать M (фразы на диске нет) → каждый подписанный M — подлинная правка владельца; противник только повторяет старое, утаивает новое и забивает сеть. Поэтому расколы решаются детерминированным объединением, а не выбором ветви.
- **CRDT 2P-Set `[Shapiro et al. RR-7506]`:** members/gone уже есть состояние 2P-Set (A = members ∪ gone, R = gone; удаление побеждает навсегда). Объединение двух состояний (A∪A', R∪R') коммутативно, ассоциативно, идемпотентно → порядок доставки, повторы, старые M ничего не ломают; подписывать слияние не нужно.
- **Tailscale Tailnet Lock `[tka/tka.go, sync.go, builder.go; tailscale.com/kb/1230]`:** AUM с хэшем родителя; развилка — `pickNextAUM`: наибольший вес подписей → RemoveKey → наименьший хэш; проигравшая ветвь отбрасывается; контрольная точка каждые 50 AUM; догоняние SyncOffer{Head, Ancestors} в обе стороны. Брать: хэш родителя, SyncOffer, правило «исключение > меньший хэш» для входа. Не брать: отбрасывание ветви (молча теряет добавление ПК).
- **TUF `[spec §1.5.2, §2.1.4, §4.3, §5.3]`:** откат — «версия не убывает» (у нас есть); заморозка — только онлайн-ключ timestamp с коротким сроком, **без сервера/кворума нерешаема**; ротация root двойной подписью — образец на будущее.
- **MLS `[RFC 9420 §14, RFC 9750 §5.3]`:** требует правила канона для конфликтующих Commit; без упорядочивающего сервиса готового ответа нет.
- **Octagon (Apple), Keybase, CONIKS, Matrix state res v2, Syncthing, Signal v2** — идеи: исключённый навсегда; сверка верхушек при встрече двух честных ПК лечит раздвоение; Syncthing — анти-пример (без надгробий удаление не держится).
- **Библиотеки (LICENSE по GitHub API):** MIT-кандидата нет. tailscale.com/tka — BSD-3-Clause, ~56 сторонних пакетов, модель не совпадает (нет members/gone/TOTP); go-tuf v2 — Apache-2.0, вокруг сервера; neurodrone/crdt — MIT, но 2P-Set — ~30 строк, брать нечего; automerge-go — MIT, cgo+Rust, избыточно. **Вывод: своё по алгоритмам (2P-Set + SyncOffer + правило развилки TKA), ~150–250 строк; лицензий не тянет.**
- **Рекомендация:** состав = join всех полученных подлинных M (2P-Set), без подписи слияния; уходят errSpaceFork по составу, флаг раскола, spaceMerge с фразой для состава. Вход (psalt/phash/totp) — регистр по цепочке lprev, при параллельных сменах: больше исключений → больший lgen → меньший хэш; если секрет победителя видел исключённый ПК — вход «скомпрометирован», пропусков нет до нового входа фразой (единственный остаток слияния с фразой). Свежесть при вступлении: показать состав владельцу в окне ввода фразы + пропуска после сверки с членом ≠ поручитель; вариант «хаб хранит подписанную верхушку (sid, хэш, глубина)» меняет решение 3 — вопрос владельцу.

  главного потока — его даёт uiStart (значок или сам детектор) при любом ANYPC_MACWIN; без графического сеанса
  uiStart = false → alive(false), «Работаю тут» отказывает. Временная проба (не в репозитории): процессу, ни разу
  не бывшему активным, доходит и наблюдателю с Coalesce при отправке без deliverImmediately — приостановка AppKit
  включается только после ухода из активных. С приостановкой (`suspended = YES` своему процессу, как AppKit
  неактивному приложению) наблюдатель с Coalesce уведомление без deliverImmediately не получает, с DeliverImmediately —
  получает `[измерено 2026-11-14, TestMacLockLive и мутация Coalesce]` — поэтому в коде DeliverImmediately.
- **Windows: у AnyPC.exe нет режима службы** (`--install-service` есть только в cli_unix.go) — программа всегда в
  сеансе пользователя, где и окно WebView2. Проверка сеанса 0 (ProcessIdToSessionId) в lock_windows.go — на будущее:
  из службы NOTIFY_FOR_THIS_SESSION видит только сеанс 0, детектор честно alive(false). До этой части на Windows
  `startLock` вообще не вызывался и выход не снимал пропуска мастера — теперь, как на unix, offAll при выходе.
  Проверено только V0/V1 (разбор сообщений, сборка); живые события сеанса — V2 владельца.
- **Windows: выключение, перезагрузка и выход из сеанса не дают main дойти до offAll** (приёмка Ч5, B1): окну
  приходят WM_QUERYENDSESSION, затем WM_ENDSESSION(TRUE), после возврата из обработчика процесс убивают, w.Run() не
  возвращается. Поэтому снятие — синхронно в обработчике WM_ENDSESSION окна детектора (≤ 3 с; система ждёт «висящее»
  приложение ~5 с `[ПРЕДПОЛОЖЕНИЕ по документации завершения сеанса, не измерено]`). WTS_SESSION_LOGOFF блокировкой не
  считаем: фоновое снятие по нему забрало бы список у синхронного (offAll отдаёт список первому вызову), а выход из
  сеанса и так приходит как WM_ENDSESSION.
- **Второй offAll не ждал летящих «снять» первого** (приёмка Ч5, B2, все ОС): фоновый offAll блокировки уносит
  p.issued сразу, в p.retry цель попадает только после неудачи — синхронный offAll (WM_ENDSESSION, выход) видел пустой
  список и возвращался, пока «снять» ещё в пути; при выходе отмена ctx программы ещё и рвала это «снять». Исправлено:
  offAll ждёт в пределах своего ctx прежние offAll с непустым списком (p.flying), затем берёт неудачные из retry; on()
  детектора — на context.WithoutCancel(ctx) (SIGTERM и выход его не рвут); на Windows offAll(quit) — до cancel().
  Регрессия — pass_fly_test.go (без p.bg.Wait()).

  тем же замком (TestPassThreeParty; мутации «один снимок», «fly не удалять», «retry не обнулять» убиты).

## Ч10.1 приём на хосте — 2026-11-15 (agent/recv.go, recv_ask.go, file.go; app/recv.go)

- **Вид соединения «приём»** — connect того же вида, что сверка/вступление/пропуск ({"view":true,"sx":…}): свой ПК — ровно connect сверки (sx запечатан к ключу цели, место ключа до "b" — то же `a.syncs`), чужой — ровно connect вступления (sx случайный, место незавершённого входа, maxPending, блокировка). Назначение («приём», не «сверка», не «вход») — только в "b" внутри DTLS (`recv:true`). Хаб различает не больше, чем сверку [вывод: поля connect и ответы хаба не менялись; тесты приёма проходят через хаб v0.3.0 — `compat.sh v0.3.0 hub`].
- **Сессия приёма не входит:** `authed` не ставится никогда → глухие "input" (гейт control), "ctl" (гейт authed: clip, pick, mode, audio), видео не стартует (stream — только из accept). Каналы клиента: только "file" и "text"; остальные закрываются. Тест TestRecvOnlyReceive; мутант «приём входит» убит.
- **Свой ПК:** ключ члена доказан дважды — sx (X25519+HKDF+AES-GCM, spseal.go, без изменений) и подпись над отпечатками DTLS в "b" (cpub должен совпасть с ключом из sx). Ключ исключили между connect и "b" или во время приёма (`SyncKey` перед каждым файлом/текстом) — отказ "gone". **Требует ревью человеком (A13).**
- **Чужой ПК, разовый код:** CPace записи по умолчанию — тот же путь и та же блокировка, что у входа кодом (`pwLocked("")`, `countAuth`: 5 неверных → 1 мин…1 ч; при блокировке код сменяется). Только в режиме «Спрашивать» (`CodeMode`): в режиме пароля запись по умолчанию — постоянный пароль владельца, чужим он не годится → отказ "nocode". Верный код израсходован (`codeUsed`), ключ отправителя закреплён (`recv_pins` в config.json: ID 9 цифр или пусто, имя по `validName`, ключ 32 байта, не больше 32, давние уходят, негодные записи из файла не действуют). **Требует ревью человеком (A13).**
- **Чужой ПК, закреплённый ключ:** без кода; первое принимаемое — окно «Принять?» (askLoop/TaskDialog как «Разрешить», AskTimeout 30 с); «Принять» на файл — и остальные файлы сессии; текст от чужого — всегда окно с текстом (не больше 600 символов и 12 строк, управляющие и Cf заменены), в буфер — только после «Принять». «Отклонить»/нет ответа — "denied", сессия закрывается. Незнакомый ключ без кода — "nokey" без неудачи в счёт перебора (ключ доказан, перебирать нечего). Отозвать — `config.recvUnpin` (окно — Ч10.5).
- **Потолки (NOTIFY, числа выбраны исполнителем):** файл ≤ 16 ГБ, файлов за сессию ≤ 64 ГБ, файлов+текстов ≤ 1000, текст ≤ 1 МБ (UTF-8), сессий с одного ключа: член — 10/мин, чужой — 3/мин (каждая может открыть окно), сессий приёма одновременно ≤ 4, без данных 2 мин — закрыта.
