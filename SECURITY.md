# Безопасность / Security

AnyPC даёт удалённое управление компьютером, поэтому об уязвимостях просим сообщать **приватно**, а не в открытых тикетах:
**Security → Report a vulnerability** (https://github.com/LoginByCall/AnyPC/security/advisories/new).

AnyPC gives remote control of a computer, so please report vulnerabilities **privately**, not in public issues:
**Security → Report a vulnerability** (link above).

Поддерживается последняя версия / Only the latest release is supported. Подпись выпусков — `SHA256SUMS.sig`, открытый ключ — в README.

Вход без подтверждения защищён вторым фактором TOTP (код из приложения-аутентификатора после пароля); файл настроек
хоста содержит оба фактора (хэш пароля и секрет TOTP), поэтому TOTP защищает от утечки пароля, но не от кражи этого файла.
«Моё пространство»: каждый ПК пространства хранит общий список ПК со всеми общими секретами (хэш пароля, секрет TOTP);
сессия, вошедшая паролем и кодом владельца, получает этот список целиком. Кража одного ПК пространства — повод
исключить его и сменить пароль. / "My space": every member PC stores the shared member list with the shared secrets;
a session logged in with the owner's password and code receives it.

«Моё пространство»: корень доверия — **фраза пространства**, отдельная от пароля входа. Из неё выводится ключ,
которым подписан состав (кто в пространстве, пароль входа, секрет кода); фраза не хранится ни на одном ПК и не
уходит в сеть — её вводят при создании пространства, вступлении ПК, исключении ПК и смене пароля входа или кода.
Храните фразу офлайн (на бумаге). Пароль входа и код дают вход и «Работаю тут», но менять состав не позволяют:
кража ПК пространства или утечка пароля входа не дают вору добавить свой ПК или исключить ваши. Утечка или потеря
фразы — создайте пространство заново (восстановления нет). Фраза — 10 случайных слов, её выдаёт программа.
Украденный ПК позволяет перебирать фразу офлайн (у каждого ПК пространства есть открытый ключ и соль владельца);
80 бит случайной фразы делают такой перебор нереальным.
"My space": the root of trust is the **space phrase**, separate from the login password. It derives the key that signs
the member list (members, login password, code secret); the phrase is stored on no PC and never sent over the
network — it is typed when creating the space, adding or removing a PC, and changing the login password or code.
Keep the phrase offline (on paper). The login password and code allow login and "Work here" but not membership
changes: a stolen member PC or a leaked login password does not let a thief add their PC or remove yours. If the
phrase leaks or is lost, create the space anew (there is no recovery). The phrase is 10 random words generated by
the program. A stolen PC allows an offline search for the phrase (every member holds the owner public key and salt);
the 80 bits of a random phrase make that search infeasible.
Login without confirmation is protected by a TOTP second factor; the host's settings file holds both factors (password
hash and TOTP secret), so TOTP protects against a leaked password, not against theft of that file.

«Моё пространство»: после «Работаю тут» (пароль и код) ключ хоста ПК «я тут» на срок пропуска — единственный фактор
входа на все ПК пространства. Пропуск снимается блокировкой экрана и выходом на том ПК, через 12 ч и перезапуском цели.
"My space": after "Work here" (password and code), the host key of the "I'm here" PC is, for the pass lifetime, the only
login factor for every PC of the space. The pass ends on screen lock or quit on that PC, after 12 h, or on target restart.
«Снять» — одно сообщение через хаб, подписанное ключом ПК «я тут» (ID цели и случайный id пропуска, который цель
выдала при входе), без соединения; снятым мастер считает пропуск только по ответу цели, подписанному её ключом хоста, и
до него повторяет. У «снять» своё ведро на хабе: задержать его можно потоком не меньше чем со 100 адресов (IPv4 или IPv6
/48) сразу; исключение — посторонний за тем же адресом, что ПК «я тут» (CGNAT, общий VPN, офис): он делит с мастером
долю адреса и задерживает «снять» с одного адреса. Цели старых версий снимаются по-старому, отдельным соединением, — там посторонний, знающий ID цели, может
потоком подключений задерживать «снять» (пропуск живёт до 12 ч или перезапуска цели). Хаб видит момент «снять»
(блокировку или выход на ПК «я тут»), ID цели, ключ ПК «я тут» (хабу он и так известен — это ключ, под которым тот ПК в
сети), id пропуска и ответ цели (снят / такого пропуска нет); может выборочно «снять» не пропускать — тогда мастер
повторяет, пока пропуск не истечёт.
"Off" is a single message via the hub, signed by the "I'm here" PC key (target ID and the random pass id the target gave
at login), with no connection; the master treats the pass as removed only on the target's reply signed with its host key,
and repeats until then. "Off" has its own hub bucket: delaying it takes a flood from at least 100 addresses (IPv4 or IPv6
/48) at once — except for an attacker behind the same address as the "I'm here" PC (CGNAT, shared VPN, office), who
shares that address's quota and can delay "off" from a single address. Targets of older versions get "off" the old way, over a separate connection, where a stranger who knows the
target ID can delay it with a flood of connections (the pass then lives up to 12 h or until the target restarts). The hub
sees when "off" is sent, the target ID, the "I'm here" PC key (already known to it as that PC's host key), the pass id
and the target's reply; it can drop "off" selectively — the master then repeats until the pass expires.

Вход по пропуску из окна (ТРЕБУЕТ РЕВЬЮ ЧЕЛОВЕКОМ): окно программы входит на ПК пространства тем же «b», что ПК «я
тут», — подписью ключом этого ПК над отпечатками этого соединения (привязка spaceSign); ключ цели окно сверяет с
составом пространства. spaceSign — оракул подписи ключом этого ПК для страниц окна, включая вкладки «Моих ПК» (они
берут привязки у окна через embed.js). Новой границы это не создаёт: процесс того же пользователя ОС и так читает ключ
из config.json (0600). Но для скрипта, исполнившегося в окне, граница новая: раньше ему нужны были пароль и код, теперь на ПК с живым пропуском он входит без них. Подпись выдаётся только для цели — члена состава с живым пропуском. Режима и записи в подписи
нет: окно с токеном может на этом соединении сверх входа послать «снять» и «b» паролем с ключом этого ПК как cpub;
пока у мастера жив пропуск на цель (passUntil), пароль так можно перебирать мимо блокировки перебора (код TOTP
по-прежнему нужен). Отдельный домен подписи не вводим: цели v0.2.0 его не примут.
Login by pass from the window (NEEDS HUMAN REVIEW): the program window logs in to a PC of the space with the same "b" as
the "I'm here" PC — a signature by this PC's key over the fingerprints of this connection (the spaceSign binding); the
window checks the target key against the space members. spaceSign is a signing oracle with this PC's key for the window
pages, including the "My PCs" tabs (they take the bindings from the window via embed.js). This adds no new boundary: a
process of the same OS user can read the key from config.json (0600) anyway. For a script running in the window, though, this is a new boundary: it used to need the password and code, now it logs in without them to a PC with a live pass. A signature is given only for a target that
is a member with a live pass. The signature covers neither the mode nor the account: a window with the token can, on
that connection, also send "off" and a password "b" with this PC's key as cpub; while the master holds a live pass for
the target (passUntil), passwords can be guessed this way past the brute-force lockout (the TOTP code is still needed).
No separate signature domain: v0.2.0 targets would not accept it.

«Добавить» в уже вошедшей сессии (ctl «trust», с v0.3.1; ТРЕБУЕТ РЕВЬЮ ЧЕЛОВЕКОМ): ключ клиента попадает во вход без
пароля записи без повторного входа. Условия те же, что у trust в «b»: вход паролем записи с кодом TOTP (не ключом, не
пропуском, не через «Разрешить»), ключ доказан подписью над отпечатками этого соединения в «b» (в ctl новый ключ не
принимается), сейчас не «Спрашивать», запись и пароль те же, ключ не исключён из пространства; один раз за сессию.
Новой возможности это не даёт: окно для trust теперь — вся сессия, а не момент входа, но посторонний скрипт в
вошедшем клиенте (веб-клиент, окно) и так держит пароль сессии (повторный вход, again.pw) и мог войти заново с trust;
а вход добавленным ключом по-прежнему требует кода TOTP. Как и trust в «b», ctl «trust» разрешён при «Только показ
экрана» на хосте и у записи с правами «просмотр»: ключ даёт ровно права записи, не больше.
"Add" in a live session (ctl "trust", since v0.3.1; NEEDS HUMAN REVIEW): the client key goes into password-less login
of the account without a second login. Same conditions as trust in "b": login with the account password and TOTP code
(not by key, pass or "Allow"), the key proven by a signature over this connection's fingerprints in "b" (no new key is
accepted over ctl), "Ask" is off now, the account and password unchanged, the key not removed from the space; once per
session. This adds no new capability: the window for trust is now the whole session rather than the login, but a
foreign script in a logged-in client (web client, window) already holds the session password (kept for a reconnect)
and could log in again with trust; and logging in with the added key still requires the TOTP code. Like trust in "b",
ctl "trust" is allowed with "Screen sharing only" on the host and for a "view" account: the key gives exactly the
account's rights, no more.

«Моё пространство», сверка состава: ПК пространства сами сверяют состав (кто в пространстве, пароль входа, секрет
кода) отдельным соединением без видео и входа — вне мест входа (их три) и вне блокировки перебора паролей; места
сессии оно не занимает, но пока на цели идёт сессия, сверке отвечают тем же «занято», что обычному подключению. Запрос
подключения сверки для хаба выглядит как обычный: каждый новый клиент (браузер, вступление, пропуск) шлёт поле той же
длины со случайными байтами, а у сверки в нём — доказательство члена (время), зашифрованное общим ключом пары «член —
цель» (X25519 из ключей ПК, HKDF, AES-GCM; ключ X25519 выводится из ключа ПК Ed25519 — ТРЕБУЕТ РЕВЬЮ ЧЕЛОВЕКОМ:
криптография). Открыть его может только цель и только ключом члена своего состава: постороннему цель не выделяет
ничего (его запрос — обычное подключение), члену — одно место на ключ. Ответ цели («сверка принята», «часы
расходятся», «занято») идёт внутри зашифрованного канала, привязан к нему и шифруется каждый раз со случайным nonce;
для обычных подключений там те же по длине случайные байты. Состав уходит только члену, и только после того, как обе
стороны доказали свои ключи; ПК, исключённый из состава, его больше не получает. Хаб больше не видит ключ ПК-члена и
ключ, которого член ждёт от цели. Неотличимость сверки от вступления и входа по пропуску (по полям, длине, кодам
ошибок) — только против пассивного хаба, который лишь смотрит. Активный хаб сверку опознаёт пробой мест: после чужого
подключения он шлёт к цели три своих — «занято» на третьем значит, что чужое заняло место входа (обычное), offer на
всех трёх — что это была сверка; так же — подключением во время блокировки перебора, когда обычным отвечают «заперто»,
а сверка получает соединение. Это следствие решения владельца 2026-11-14 (A: сверка проходит при блокировке и занятых
местах входа, чтобы посторонний не мешал сверке) — решение владельца 2026-11-14: A, окончательно. Что хаб видит и
пассивно (остаточные утечки): адрес IP клиента и ID цели — а ПК-член подключается к хабу как хост с того же адреса,
так что пару «ПК с этого адреса ходит служебным соединением к цели» хаб связать может (сверка это, вступление или
пропуск — не знает); соединение программы отличается от браузерного заголовками и значениями полей (замеры TURN);
время: при запуске программа сверяется со всеми членами сразу, потом раз в 5–15 мин (случайно) — с одним случайным,
повторы — со случайной паузой; в минуты блокировки перебора или занятых мест входа — сравнение с отказами обычным
подключениям; время ответа цели: перебор ключей состава одинаков у сверки и обычного подключения (общие секреты пар
считаются один раз и держатся только в памяти, перебор всегда полный и не короче 64 ключей), так что сверку от
обычного подключения по нему не отличить — остаются единицы микросекунд (замер на ПК разработки: около 2 мкс из 75) на
фоне миллисекунд сети. Размер состава грубо оценим: первое подключение после перезапуска цели (его хаб видит по
регистрации) или смены состава дольше на 80–170 мкс за каждый новый ключ (около +3,5 мс при 32 ключах, +6 мс при 64) —
у любого подключения, сверка это или нет. Остаточный канал, ТРЕБУЕТ РЕВЬЮ ЧЕЛОВЕКОМ: кэш повтора сверки (соли за 10
минут) чистится линейным проходом только при сверке — её время растёт с числом недавних сверок на цели. Хаб, вставший
посредником в шифрование канала (он пересылает его описание), ключа члена не получит: ответ цели зашифрован ключом,
который знают только член и цель, и привязан к отпечаткам канала, а nonce каждого ответа случаен, так что подделать
«сверка принята» хаб не может и после повторов перехваченного запроса; клиент проверяет ответ до того, как назвать
себя, затем спрашивает ключ цели («who», подпись над отпечатками канала) — у посредника подпись не сходится, и клиент
кончает; по такому обрыву и по самому «who» хаб может догадаться о служебном соединении. Повтор хабом перехваченного
запроса цель узнаёт и ведёт как обычное подключение; по ответам на повторы хаб не узнаёт ни статус, ни ключ; после
перезапуска цели в пределах 10 минут повтор может занять место этого члена до 20 секунд. Хаб может не пропускать
сверку — состав тогда не обновится, пока она не пройдёт. Остаточный риск: ПК, вступающий через ПК, у которого старый
подлинный состав, где других членов нет, проверить свежесть не может — такой ПК сверять не с кем. Выйти из
пространства на одном ПК (без фразы) можно паролем и кодом этого ПК: состав с него удаляется, пароль и код остаются.
Новый ПК после вступления не пускает вход паролем в запись по умолчанию, пока не сверится с членом, кроме поручителя
(решение 12 A; «Спрашивать» с одноразовым кодом с экрана и гости открыты); выход из пространства до такой сверки
стирает пароль и код записи по умолчанию — они из непроверенного состава поручителя.
"My space", member list sync: member PCs reconcile the member list (members, login password, code secret) over a
separate connection without video or login — outside the login slots (three) and the password brute-force lockout; it
does not take the session slot, but while the target is in a session a sync gets the same "busy" as an ordinary
connect. To the hub the sync connect request looks ordinary: every new client (browser, join, pass) sends a field of
the same length with random bytes, and for a sync it carries the member's proof (the time) encrypted with the pair key
"member — target" (X25519 from the PC keys, HKDF, AES-GCM; the X25519 key is derived from the PC's Ed25519 key — NEEDS
HUMAN REVIEW: cryptography). Only the target can open it, and only with the key of a member in its list: a stranger
gets nothing (its request is an ordinary connect), a member gets one slot per key. The target's answer ("sync
accepted", "clocks differ", "busy") goes inside the encrypted channel, is bound to it and is encrypted with a fresh
random nonce each time; ordinary connections get random bytes of the same length there. The list goes only to a member
and only after both sides proved their keys; a PC removed from the list no longer gets it. The hub no longer sees the
member key or the key the member expects from the target. A sync is indistinguishable from a join or a pass login (by
fields, length, error codes) only to a passive hub that just watches. An active hub identifies a sync by probing the
slots: after someone else's connect it sends three of its own to the target — "busy" on the third means that connect
took a login slot (ordinary), an offer on all three means it was a sync; likewise with a connect during the
brute-force lockout, when ordinary connects get "locked" and a sync gets a connection. This follows from the owner
decision of 2026-11-14 (A: a sync passes the lockout and full login slots, so a stranger cannot block syncs) — owner
decision 2026-11-14: A, final. What even a passive hub sees (residual leaks): the client IP and the target ID — and a
member PC is also connected to the hub as a host from the same address, so the hub can link "the PC at this address
makes a service connection to the target" (not whether it is a sync, a join or a pass); a connection from the program
differs from a browser one by headers and field values (TURN measurements); timing: at start the program syncs with
all members at once, then every 5–15 min (random) with one random member, retries with random pauses; during a
brute-force lockout or with full login slots — comparison with refusals to ordinary connects; the target's response
time: scanning the member keys costs the same for a sync and an ordinary connect (the pair secrets are computed once
and kept in memory only, the scan is always full and at least 64 keys long), so it does not tell a sync from an
ordinary connect — what remains is a few microseconds (measured on the dev PC: about 2 µs of 75) against milliseconds
of network. The list size can be roughly estimated: the first connect after the target restarts (which the hub sees by
the registration) or after a list change is slower by 80–170 µs per new key (about +3.5 ms with 32 keys, +6 ms with
64) — for any connect, sync or not. Residual channel, NEEDS HUMAN REVIEW: the sync replay cache (salts of the last 10
minutes) is cleaned by a linear pass on syncs only — its time grows with the number of recent syncs at the target. A
hub that puts itself into the channel encryption (it relays the channel description) does not get the member key: the
target's answer is encrypted with a key only the member and the target know and is bound to the channel fingerprints,
and every answer has a random nonce, so the hub cannot forge "sync accepted" even after replaying a captured request;
the client checks the answer before identifying itself, then asks for the target key ("who", signed over the channel
fingerprints) — the man in the middle's signature does not match and the client stops; from that abort and from the
"who" itself the hub may guess a service connection. A replay of a captured request is recognised by the target and
handled as an ordinary connect; the answers to replays reveal neither the status nor the key; within 10 minutes after
the target restarts a replay can hold that member's slot for up to 20 seconds. The hub can drop syncs — the list then
stays old until a sync passes. Residual risk: a PC joining through a PC that holds an old genuine list with no other
members cannot check freshness — there is no one else to ask. A PC can leave the space locally (without the phrase)
with its password and code: the list is removed from it, the password and code stay. A newly joined PC refuses
password login to the default account until it has synced with a member other than the one it joined through (owner
decision 12 A; "Ask" with the one-time code from its screen and guests stay open); leaving the space before that sync
erases the default account's password and code, since they came from the guarantor's unverified list.

«Моё пространство», вступление нового ПК (Ч12б, решения владельца B и A'; ТРЕБУЕТ РЕВЬЮ ЧЕЛОВЕКОМ): вступление через
ПК пространства (поручитель) требует кода из приложения, фразы и человека у поручителя; пароль новому ПК не нужен.
Фразу новый ПК доказывает подписью ключом владельца (тот же ключ из фразы, что подписывает состав) над доменом
«anypc-space-join-v1», ID поручителя, DTLS-отпечатками обоих концов этого соединения и своим ключом, доказанным в том
же соединении. Домен отличен от домена подписи состава — одна не сходит за другую; перенос доказательства в другое
соединение или другому ключу не проходит. Ключ поручителя новому ПК при первом вступлении незнаком (TOFU): новый ПК
проверяет только, что ответивший доказал владение каким-то ключом над этим соединением. Поэтому самозванец под ID
поручителя (например, хаб) получает от нового ПК текущий код и подпись ключом владельца над солью, которую выбрал сам;
по этой подписи он может проверять догадки о фразе офлайн. Стойкость тогда — 80 бит случайной фразы и Argon2id (64 МБ)
на каждую догадку; код без пароля теперь проверяем сам по себе (6 цифр — только онлайн у настоящего ПК, с
блокировкой). Соль ключа владельца настоящий поручитель отдаёт только после верного кода; открытого ключа владельца до
вступления новый ПК не получает. Неверный код или неверная фраза — неудача вступления: своя лестница поручителя, как у
пароля (5 подряд — 1 минута, дальше удвоение до часа); вход владельца (пароль, код, закреплённый ключ) она не
запирает; окна нет. После верных кода и фразы поручитель показывает окно «Пустить ПК «имя» в ваше пространство?» с ID,
именем (их заявляет новый ПК; без ID вступление отклоняется) и отпечатком его ключа; «Разрешить» срабатывает через 3–5
с; без ответа 2 минуты — отказ; окно не смогло появиться (нет сеанса рабочего стола, zenity, MessageBoxTimeoutW) —
отказ с отдельной причиной. Окно на хост одно; после «Отклонить» или тайм-аута следующее — не раньше чем через 30 с,
каждый следующий отказ подряд — вдвое дольше (до 16 минут; «Разрешить» или час тишины сбрасывают), смена ID или ключа
паузу не обходит. Ушёл вступающий — окно закрывается (на Windows запасное окно MessageBox закрыть нельзя — оно
доживает свой срок, второе при нём не открывается). Сессия вступления — не вход: ни экрана, ни ввода, ни буфера;
только выдача состава и приём нового, где новый ПК — под ID из окна и с ключом из соединения; живёт до 4 минут. Вход
паролем (новые ПК с AnyPC версий до 0.3.1 включительно) на новом поручителе получает состав тоже только после «Разрешить» (в окне ID
и имя, если клиент их сообщил; старая версия — без ID), ввод этой сессии на время окна выключен — обойти окно старым
протоколом нельзя. Поручитель версии до 0.3.1 включительно вступления без пароля не объявляет: новый ПК идёт прежним путём с
паролем, окна там нет. Доступность поручителя (остаточное): незавершённая попытка без кода держит место незавершённого
входа до 40 с (до 20 с до запроса вступления и до 20 с на код), с верным кодом — ещё до 30 с на доказательство фразы,
как любое подключение. Лестница вступления по коду — одна на поручителя: посторонний без кода, зная только ID, пятью
неверными кодами закрывает вступление по коду через этот ПК на минуту, а дальше одним неверным кодом раз в час держит
его закрытым бессрочно (каждая неудача удлиняет блокировку до часа). Тупика нет (решение владельца C): запертый
поручитель отвечает отдельной причиной, и новый ПК вступает запасным путём — паролем пространства, кодом и фразой, с
тем же обязательным окном «Разрешить» (ввод сессии на время окна выключен, пауза окон общая); неудачи пароля идут в
обычную лестницу входа записи, не в лестницу вступления. Чтобы закрыть и этот путь, атакующему нужно запереть ещё и
вход паролем — это и раньше мог делать посторонний перебором паролей (он запирает и вход владельца паролем, но не
закреплённым ключом); без пароля запасной путь ничего нового не даёт. Повторяющаяся блокировка — повод сменить код. С
верными кодом и фразой окно и вступление занимают поручителя («занят» для других подключений, в том числе владельца)
до 2 минут окна и до 4 минут после «Разрешить»; уход вступающего после 3 с окна считается как «нет ответа» и удлиняет
паузу, новые окна — не чаще растущей паузы. Бессрочно отрезать владельца знающий код и фразу не может, но может раз в
паузу занимать поручителя на несколько минут (тогда смените код фразой). ID и имя в окне — заявленные, ID
подтверждается позже сверкой (под этим ID должен ответить тот же ключ).
"My space", joining a new PC (part 12b, owner decisions B and A'; NEEDS HUMAN REVIEW): joining through a PC of the
space (the guarantor) needs the authenticator code, the phrase and a person at the guarantor; the new PC needs no
password. It proves the phrase with a signature by the owner key (the same phrase-derived key that signs the member
list) over the domain "anypc-space-join-v1", the guarantor ID, the DTLS fingerprints of both ends of this connection
and its own key proven on the same connection. The domain differs from the member-list signature domain — neither
passes for the other; a proof moved to another connection or another key fails. On a first join the guarantor key is
unknown to the new PC (TOFU): it only checks that whoever answers proved some key over this connection. So an impostor
under the guarantor ID (e.g. the hub) gets the current code and a signature by the owner key over a salt of its own
choice, and can test phrase guesses offline against it. Strength then rests on the 80-bit random phrase and Argon2id
(64 MB) per guess; without a password the code is checkable on its own (6 digits — online only, at the real PC, with
lockout). The real guarantor gives out the owner-key salt only after a correct code; the new PC gets no owner public
key before joining. A wrong code or phrase is a join failure: a separate ladder on the guarantor, like the password
one (5 in a row — 1 minute, then doubling up to an hour); it does not lock the owner's login (password, code, pinned
key); no window. After a correct code and phrase the guarantor shows "Let PC “name” into your space?" with the ID, the
name (both claimed by the new PC; a join without an ID is refused) and its key fingerprint; "Allow" works after 3–5 s;
no answer within 2 minutes — refused; if the window cannot appear (no desktop session, zenity, MessageBoxTimeoutW) —
refused with its own reason. One window per host; after "Deny" or a timeout the next one comes no sooner than 30 s
later, each further refusal in a row doubles that (up to 16 minutes; "Allow" or an hour of quiet resets it); changing
the ID or key does not bypass the pause. If the joining PC leaves, the window closes (on Windows the fallback
MessageBox cannot be closed — it lives out its time, and no second window opens meanwhile). The join session is not a
login: no screen, input or clipboard; only handing out the list and taking the new one, where the new PC is under the
ID from the window with the key from the connection; it lives up to 4 minutes. A password login (new PCs with AnyPC
0.3.1 or older) on a new guarantor also gets the list only after "Allow" (the window shows the ID and name if the
client reports them; an old version — without an ID), and that session's input is off while the window is open — the
window cannot be bypassed with the old protocol. A guarantor of 0.3.1 or older does not announce password-less
joining: the new PC takes the old password path, with no window there. Guarantor availability (residual): an
unfinished attempt without the code holds an unfinished login slot for up to 40 s (up to 20 s before the join request
and up to 20 s for the code), with a correct code up to 30 s more for the phrase proof, like any connection. The
join-by-code ladder is one per guarantor: a stranger who knows only the ID closes joining by code through this PC for
a minute with five wrong codes and then keeps it closed indefinitely with one wrong code an hour (each failure extends
the lock up to an hour). It is no dead end (owner decision C): a locked guarantor answers with its own reason, and the
new PC joins by the fallback path — the space password, the code and the phrase, with the same mandatory "Allow"
window (the session's input is off while it is open, the window pause is shared); password failures go to the usual
login ladder of the account, not to the join ladder. To close this path too, an attacker must also lock password login
— which a stranger could already do by guessing passwords (it locks the owner's password login too, but not login with
a pinned key); without the password the fallback gives nothing new. A recurring lock is a reason to change the code.
With a correct code and phrase the window and the join make the guarantor busy for other connections, the owner's
included, for up to 2 minutes of window and up to 4 minutes after "Allow"; the joining PC leaving after 3 s of window
counts as "no answer" and lengthens the pause; new windows come no faster than the growing pause. Whoever knows the
code and phrase cannot cut the owner off indefinitely, but can occupy the guarantor for a few minutes once per pause
(then set a new code with the phrase). The ID and name in the window are claimed; the ID is confirmed later by sync
(the same key must answer under that ID).

«Моё пространство», объединение составов: каждый подписанный фразой состав — подлинная правка владельца, поэтому ПК
не выбирает «правильную ветвь», а объединяет все известные составы: исключённые — объединение, члены — объединение
без исключённых. Исключённый ПК не возвращается никогда, повтор старых составов ничего не меняет, правки, сделанные
на разных ПК без связи, не теряются, расколов нет. Пароль входа и код — один на пространство: из встречных смен
побеждает та, где больше исключений, затем более поздняя, затем по хэшу — одинаково на всех ПК; проигравшая смена
пароля пропадает (её нужно повторить). ПК, пропустивший смены пароля, сразу переходит на новый, как только получил
любой свежий состав, — старый пароль на нём перестаёт действовать. Если в объединении исключён ПК, которого не было
среди исключённых, когда задавали победивший вход (встречные исключения: он мог получить секрет кода сверкой), вход
«скомпрометирован»: пропусков «Работаю тут» и вступлений нет, пока правка фразой не задаст новый код. Смена входа
(пароля или кода, в том числе при повторном вступлении) рвёт сессии записи по умолчанию — и на ПК без пространства:
новый секрет кода записи по умолчанию рвёт её сессии всегда; исключение ПК рвёт его
сессии, а при входе без ключа члена (браузер, чужой ключ) — любую такую сессию. Сессия с доказанным ключом
исключённого ПК рвётся в любом режиме (и «Спрашивать») и для любой записи. Больше 16 параллельных правок —
непринятые правки хранятся и уже действуют (исключённые не члены), но пропусков нет, пока на этом ПК не будет правки
фразой или не придёт правка, сводящая их. Испорченная запись состава в настройках — пространства на этом ПК нет (пропусков и сверки нет): выйти
из пространства паролем и кодом и вступить снова. Ответы «под этим ID другой ПК» и «часы расходятся»
только показываются в окне и на решения не влияют. Повтор сверки с недоступным ПК — не дольше часа, дальше сверка
периодически и при запуске.
"My space", merging member lists: every list signed with the phrase is a genuine owner edit, so a PC does not pick a
"right branch" but merges all lists it knows: removed PCs — the union, members — the union minus removed. A removed
PC never comes back, replaying old lists changes nothing, edits made on different PCs without contact are not lost,
there are no forks. The login password and code are one per space: of concurrent changes the one with more removals
wins, then the later one, then by hash — the same on every PC; the losing password change is dropped (repeat it). A PC
that missed password changes switches to the new one as soon as it gets any fresh list — the old password stops
working there. If the union has a removed PC that was not removed yet when the winning login was set (concurrent
removals: it could have got the code secret by sync), the login is "compromised": no "Work here" passes and no joins
until an edit with the phrase sets a new code. A login change (password or code, also on joining again) drops
sessions of the default account — also on a PC without a space: a new code secret of the default account always
drops its sessions; removing a PC drops its sessions, and for a login without a member key (browser,
foreign key) any such session. A session with the proven key of a removed PC is dropped in any mode ("Ask" too)
and for any account. More than 16 concurrent edits — the refused edits are kept and already apply (removed
PCs are not members), but no passes until an edit with the phrase on this PC or an incoming edit that merges them. A damaged list in the settings
— no space on this PC (no passes, no sync): leave the space with the password and code and join again. The replies "another PC under this ID" and "clocks differ" are only shown in the window and change no
decision. Retrying sync with an unreachable PC lasts at most an hour, then sync runs periodically and at start.

Приём файлов и текста на этот ПК (Ч10.1, ТРЕБУЕТ РЕВЬЮ ЧЕЛОВЕКОМ: проверка ключа члена, разового кода и
закреплённого ключа). Соединение приёма для хаба выглядит как сверка (свой ПК) или вступление (чужой ПК): поля
подключения, отказы «занят»/«заблокирован» и ответы те же, назначение — только внутри шифрованного канала. Что хаб
всё же видит: длительность соединения и объём трафика (через TURN), а свой ПК при заполненных местах входа получает
offer, а не «занят», — как сверка. Сессия приёма не входит: ни экрана, ни ввода, ни буфера в обратную сторону, ни
звука; принимаются только файлы (в «Загрузки») и текст (в буфер обмена). «Только показ экрана» запрещает и приём.
Свой ПК: ключ члена состава доказан запечатанным полем подключения и подписью над отпечатками канала; ключ исключили —
приём рвётся; до сверки нового ПК с членом ≠ поручитель приём закрыт. Чужой ПК: первый раз — разовый код с экрана
получателя (тот же код и та же блокировка перебора, что у входа; код расходуется), затем ключ отправителя закреплён
и дальше — окно «Принять?» без кода; незнакомый ключ без кода — отказ. Для владельца: один и тот же разовый код
открывает и вход, и приём — не диктуйте его тому, кому не доверили бы и вход; свой ПК кладёт текст в буфер обмена
молча, заменяя то, что там было; имя и ID, с которыми закреплён отправитель, заявляет он сам (доказан только ключ);
«Принять» на первый файл принимает все файлы этой передачи (но не следующей); файлам от чужого ставится метка
«из интернета» (Windows — Zone.Identifier, macOS — com.apple.quarantine; не проверено на Windows и Маке, V2), на
Linux её нет. Текст перед буфером обмена очищается от управляющих символов (кроме табуляции и переводов строки) и
от подмен направления письма (U+202A–202E, U+2066–2069); соединители (эмодзи, персидский) и мягкий перенос остаются.
Потолки: файл 16 ГБ, 64 ГБ и 1000 файлов за сессию, текст 1 МБ, 4 сессии сразу; свой ПК — 10 сессий в минуту с
одного ключа, чужой ключ — одна сессия сразу и 3 в минуту. Сессия закрывается без сообщений 2 минуты (пока открыто окно «Принять?» — нет), а
после 30 минут — как только байты перестали идти или идут медленнее 64 КБ/с за 2 минуты (длинный файл, который идёт,
не обрывается; до 30 минут скорость не проверяется — мелкие файлы по медленному каналу).

Receiving files and text on this PC (Ch10.1, NEEDS HUMAN REVIEW: member key, one-time code and pinned key checks).
To the hub a receive connection looks like a sync (own PC) or a join (foreign PC): the connect fields, the
"busy"/"locked" refusals and the answers are the same; the purpose is only inside the encrypted channel. What the hub
still sees: the connection's duration and traffic volume (via TURN), and an own PC gets an offer rather than "busy"
when the login slots are full, as a sync does. A receive session never logs in: no screen, no input, no clipboard
back, no audio; only files (to Downloads) and text (to the clipboard). "View only" forbids receiving too. Own PC: the
member key is proven by the sealed connect field and by a signature over the channel fingerprints; a removed key
stops the receive; until a new PC has synced with a member other than its sponsor, receiving is closed. Foreign PC:
the first time, the one-time code from the receiver's screen (the same code and the same brute-force lock as login;
the code is used up), then the sender's key is pinned and later sends show an "Accept?" window without a code; an
unknown key without a code is refused. For the owner: the same one-time code opens both login and receiving — do not
give it to someone you would not let log in; an own PC replaces the clipboard silently; the name and ID a sender is
pinned with are claimed by the sender (only the key is proven); "Accept" on the first file accepts all files of that
transfer (not the next one); files from a foreign PC get the "from the internet" mark (Windows — Zone.Identifier,
macOS — com.apple.quarantine; not verified on Windows and Mac, V2), Linux has none. Text is cleaned before the
clipboard: control characters (except tab and line breaks) and writing-direction overrides (U+202A–202E,
U+2066–2069) are removed; joiners (emoji, Persian) and soft hyphens stay. Limits: 16 GB per file, 64 GB and 1000
files per session, 1 MB of text, 4 sessions at once; an own PC — 10 sessions per minute per key, a foreign key — one
session at a time and 3 per minute. A session is closed after 2 minutes without messages (not while an "Accept?" window is
open), and after 30 minutes as soon as bytes stop flowing or flow slower than 64 KB/s over 2 minutes (a long file
that is moving is not cut; speed is not checked during the first 30 minutes — small files over a slow link).

Отправка: избранные и закреплённые отправители (Ч10.4–10.5, ТРЕБУЕТ РЕВЬЮ ЧЕЛОВЕКОМ: сопоставление ключей при отзыве,
метки выбора, уведомления). Избранное — только ID и имя на этом ПК; ключ того ПК — прежний запомненный отпечаток (тот
же, что проверяется при подключении для управления), в избранные ПК попадает только после того, как его ключ доказан
отправкой (по коду или по запомненному ключу); страница окна добавить избранное не может — только переименовать. «Убрать» стирает запись; галочка «и запретить ему присылать мне без
кода» снимает закрепление того ПК как отправителя СЮДА — по доказанному ключу (запомненный отпечаток этого ID равен
отпечатку закреплённого ключа), а не по ID, который отправитель заявил при закреплении. Закрепление ЭТОГО ПК на том
отсюда снять нельзя — только владельцу того ПК («Доступ к этому ПК» → «Кто может присылать сюда без кода» →
«Отозвать»). Выбор файлов и папок — только окном ОС; странице — одноразовая метка (живёт час); если отправка не
отправила ни байта (неверный код, нет связи, отказ, отмена до начала), метки возвращаются с прежним сроком —
повтор без нового окна выбора; окно уязвимой страницы получает этим не больше, чем неиспользованная метка. Трей
отправляет выбранный в окне ОС файл своим ПК и избранным без главного окна; итог — уведомление ОС (имя ПК и имя
файла, без пути).

Sending: favorites and pinned senders (Ch10.4–10.5, NEEDS HUMAN REVIEW: key matching on revoke, picker tokens,
notifications). A favorite is only an ID and a name on this PC; that PC's key is the existing remembered fingerprint
(the same one checked when connecting for control), and a PC becomes a favorite only after its key is proven by a send
(by code or by the remembered key); the window page cannot add a favorite, only rename one. "Remove" deletes the entry; the checkbox "and stop it from sending to me without a
code" removes that PC's pin as a sender TO this PC — matched by the proven key (the remembered fingerprint of this ID
equals the fingerprint of the pinned key), not by the ID the sender claimed when pinned. This PC's pin on that PC
cannot be removed from here — only by that PC's owner ("Access to this PC" → "Who can send here without a code" →
"Revoke"). Files and folders are chosen only in the OS picker; the page gets a one-time token (one hour); if a send
delivered no byte (wrong code, no connection, refusal, cancel before the start) the tokens are returned with their
original expiry — retry without a new picker; a compromised page gains no more than from an unused token. The tray
sends a file chosen in the OS picker to own PCs and favorites without the main window; the result is an OS
notification (PC name and file name, no path).

Папки и отправка с этого ПК (Ч10.2–Ч10.3, ТРЕБУЕТ РЕВЬЮ ЧЕЛОВЕКОМ: проверка путей и выбор доказательства
получателя). Папка принимается в новую «Загрузки/<имя папки>» (занято — «<имя> (1)»…), каждый файл — по
относительному пути внутри неё. Путь отклоняется целиком, если в нём «..», «.», пустая составляющая (абсолютный путь,
«//»), «\» или «:» (UNC, «\\?\», «C:», потоки NTFS), имя устройства Windows (CON, NUL.txt, COM1…), управляющие
символы и NUL, подмены направления письма (U+202A–202E, U+2066–2069), глубже 32 составляющих, длиннее 1024 байт или
составляющая длиннее 255 байт; «<>"|?*» заменяются на «_», точки и пробелы в конце имени отбрасываются. Всё пишется
через os.Root каталога «Загрузок»: ни ссылка, ни точка повторной обработки Windows не выведут за него; каждая папка
пути должна быть настоящей папкой (не ссылкой) — иначе файл отклонён; ссылку с именем папки или файла приёмник не
трогает, а берёт следующее свободное имя. Сам каталог «Загрузок» может быть ссылкой (так его переносят) — по ней
идём. Потолки приёма действуют на сумму файлов папки; пустые папки не передаются. Отправитель: внутри отправляемой
папки символьные ссылки, устройства и FIFO не идут (список пропущенного — в итоге), файлы открываются через os.Root
папки. Свой ПК — по ключу из состава пространства, без кода; чужой — разовым кодом с его экрана (ключ того ПК после
этого запоминается, как после входа) или без кода по запомненному ключу, если тот ПК закрепил этот. В журнале
отправителя — одна строка без путей и текста. Буфер обмена отправляется только по явному выбору. Что отправить, страница
не указывает путями: файл или папку выбирает человек в окне выбора ОС, страница получает только одноразовую метку.

Folders and sending from this PC (Ch10.2–Ch10.3, NEEDS HUMAN REVIEW: path checks and how the recipient is proven).
A folder is received into a new "Downloads/<folder name>" (taken — "<name> (1)"…), each file at its relative path
inside it. A path is refused whole if it has "..", ".", an empty component (absolute path, "//"), "\" or ":" (UNC,
"\\?\", "C:", NTFS streams), a Windows device name (CON, NUL.txt, COM1…), control characters or NUL,
writing-direction overrides (U+202A–202E, U+2066–2069), more than 32 components, more than 1024 bytes, or a
component longer than 255 bytes; "<>"|?*" become "_", trailing dots and spaces are dropped. Everything is written
through an os.Root of the Downloads folder: neither a symlink nor a Windows reparse point leads out of it; every folder
of the path must be a real folder (not a link), otherwise the file is refused; a link named like the folder or the
file is not touched — the next free name is used. Downloads itself may be a link (that is how it is moved) and is
followed. The receive limits apply to the sum of the folder's files; empty folders are not sent. Sender: inside the
folder being sent symlinks, devices and FIFOs are not sent (the skipped list is in the result), files are opened
through the folder's os.Root. Own PC — by the key from the space membership, no code; foreign — by the one-time code
from its screen (that PC's key is then remembered, as after a login) or without a code by the remembered key if that
PC pinned this one. The sender's log has one line without paths or text. The clipboard is sent only when chosen. The page does not name
what to send by path: the person picks the file or folder in the OS picker, the page only gets a one-time token.
Независимые профили доступа (2026-11-26, ТРЕБУЕТ РЕВЬЮ ЧЕЛОВЕКОМ: выбор профиля и два CPace в первом «a»). Permanent
«My space» включается «Allow space» и принимает только записи с паролем и TOTP; выключение закрывает этот путь входа,
но не влияет на одноразовый код. One-time «Allow control» после запуска выключен (не хранится в файле). Выключен —
код не показывается, а one-time CPace отвечает солью кода и случайным 32-байтным секретом (новым при каждом
выключении): любой код получает тот же "fail", что неверный, с общим счётом неудач и блокировкой. Включение выдаёт
новый код. Правильный ID+Code ведёт сразу к сессии: без TOTP, окна «Разрешить», входа ключом, trust и прав пространства;
после сессии код меняется. «View Only» сужает только one-time сессии и не меняет права permanent-записей.

В новом первом "a" основной CPace — one-time, а `psalt`/`pmsg` — permanent записи по умолчанию; клиент permanent
отвечает "b" с `permanent:true`, именные записи используют прежний второй "a" с именем. Старый клиент без поля
`permanent` остаётся на основном one-time CPace. Со старым хостом новый клиент использует его единственный CPace,
как раньше. Отключение одного профиля не раскрывает состояние другого и не меняет его соль/секрет.

Independent access profiles (2026-11-26, NEEDS HUMAN REVIEW: profile selection and two CPace exchanges in the first
"a"). Permanent "My space" is enabled by "Allow space" and accepts only accounts with a password and TOTP; disabling
it closes that login path without affecting the one-time code. One-time "Allow control" is off after startup (not
stored in the file). While off, no code is shown and the one-time CPace uses the code salt and a random 32-byte
secret (new on every switch-off): every code gets the same "fail" as a wrong one, with the same failure count and
lockout. Enabling issues a new code. A valid ID+Code opens a session immediately: no TOTP, Allow window, key login,
trust or space rights; the code rotates after the session. "View Only" restricts only one-time sessions and does not
change permanent account rights.

In the new first "a", the main CPace is one-time and `psalt`/`pmsg` carry the permanent default account; a permanent
client answers "b" with `permanent:true`, while named accounts keep the existing second "a" with the name. An old
client without `permanent` stays on the main one-time CPace. With an old host, a new client uses its only CPace as
before. Disabling either profile reveals nothing about the other and does not change its salt or secret.

Системная авторизация настроек (2026-11-26): изменение доступа, пользователей, TOTP, одноразового кода и своего узла
требует подтверждения операционной системой. Windows вызывает CredUIPromptForWindowsCredentialsW и сразу затирает
возвращённый буфер (RtlSecureZeroMemory + CredFree); Linux — polkit CheckAuthorization с AllowUserInteraction;
macOS — LocalAuthentication evaluatePolicy(deviceOwnerAuthentication). Пароль AnyPC для настроек и отдельная ключевая
фраза для них не создаются и не хранятся. TOTP требуется только для входа каждого постоянного пользователя My space.
Без успешной авторизации API не меняет настройки. Проверяемые операции обёрнуты authDo/authResult: отказ возвращается
окну, действие не выполняется.

Allow control — и сетевой выключатель AnyPC: пока он выключен, runner не запускает сигнализацию и фоновую сверку
пространства. Выключение останавливает их и отменяет дальнейшие попытки подключения; включение запускает заново.
Поэтому статус показывает выключенный профиль, а не ошибку сервера.

System authorization for settings (2026-11-26): changing access, users, TOTP, the one-time code or the own server
requires operating-system authorization. Windows uses CredUIPromptForWindowsCredentialsW and immediately wipes the
returned buffer (RtlSecureZeroMemory + CredFree); Linux uses polkit CheckAuthorization with AllowUserInteraction;
macOS uses LocalAuthentication evaluatePolicy(deviceOwnerAuthentication). No AnyPC settings password or settings key
phrase is created or stored. TOTP is required only for each permanent My space user signing in, not for settings changes.
API wrappers authDo/authResult return the authorization failure to the window without applying the action.

Allow control is also AnyPC's network switch: while off, the runner does not start signaling or background space sync.
Turning it off stops both and prevents further connection attempts; turning it on starts them again. The status reports
the disabled profile, not a server error.
